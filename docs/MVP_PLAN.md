# 猫狗大战塔防主方案 v0.4

修订日期：2026-10-07

## 1. 目标与当前状态

目标是先完成真实猫狗的 3 波单机实时 3D 塔防切片，再从同一源工程分别完成 Windows Steam、Android TapTap 和抖音小游戏版本。第一交付必须可以从加载进入、下令建造、开波，一直玩到胜利或失败，再正常重开。

本次只完善设计、目标效果图和 GitHub 规划；游戏代码、猫狗模型、战斗模拟、性能与完整试玩均未开始，不安装软件、不部署。下文参数是首测基线。文档写明解决办法，不能代替后续实测；已知风险见[重点风险与解决方案](RISKS_AND_SOLUTIONS.md)，执行进度见[执行清单](EXECUTION_CHECKLIST.md)。

## 2. 第一切片范围

### 必须做

- 横屏、固定斜俯视，一张桥地图、一条固定路线、一颗猫方水晶。
- 拟人双足的工程猫、盾猫、弩猫与普通狗；角色轮廓、装备、动作能区分。

探索、手控主角战斗、对推、狗方基地、第二地图、随机掉落、永久养成、联网、重型通用框架，以及升级、拆除、全体加速支援。

## 3. 多平台制作路线

### 3.1 一个源工程，三个构建目标

采用 **Cocos Creator 3.8 LTS + TypeScript + 实时 3D**。Blender 保存模型、骨骼、动作与装备源文件，glTF／GLB 作为交换格式，最终在 Cocos 导入结果上检查材质和动画。[Cocos 官方跨平台说明](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/index.html)列出了 Windows、Android、Web 与抖音小游戏等构建目标。

| 目标出口 | 游戏产物与输入 | 开发与验收边界 |
| --- | --- | --- |
| Steam | Windows 原生程序；鼠标为完整操作入口，键盘提供取消／暂停等补充 | 需要 Windows 原生构建与 Windows 设备验证；Steam 商店和上传后置 |
| TapTap | Android 原生安装包；触屏完整操作 | 后续需要 Android 工具链、签名和真机；不能把 Web 预览称作 APK |
| 抖音 | Cocos 抖音小游戏专用构建；触屏、安全区、平台暂停恢复 | 按普通 Cocos 小游戏规则处理包体与加载，后续经开发者工具和宿主真机验证 |

三端共用玩法、配置与源资产，可有不同贴图压缩、画质、输入和资源打包。不能复制三套战斗逻辑，也不能把一个包当作全平台完成。Steam 首版目标只覆盖 Windows；Mac 是日常开发环境，不代表首版另增 macOS 商业发行或 Steam Deck 支持。

Mac 负责 Cocos 编辑、TypeScript、Blender 资产与 Web 预览。Cocos 官方 Windows 流程要求 Windows 电脑与 Visual Studio 2019／2022 C++ 环境；Windows 编译／测试环境后续单独安排。[Windows 构建示例](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/windows/build-example-windows.html)

开工时记录实际 Cocos 3.8.x 补丁版本并固定，不在过程中无记录地升级。此前只读环境检查见 Node 20.6.0、Blender 4.5.13 LTS，仅为历史观察，不能推出 Cocos 已安装、工具已兼容或三端可构建。本轮不安装 Cocos、Android Studio／SDK、抖音开发者工具或 Visual Studio。

### 3.2 最小架构分工

| 层与职责 | 内容 | 不得混入 |
| --- | --- | --- |
| Core／Clock | 固定步时钟、局状态、稳定 ID、输入命令与事件顺序 | Cocos 节点、系统时间、平台 API |
| Core／Route 与 Battle | 路线进度、阻挡、放行、攻击、飞箭命中、伤害与死亡 | 动画回调扣血、刚体推挤决定规则 |
| Core／Construction 与 Economy | 施工任务、战位锁定、取消、唯一扣款退款 | UI 直接修改余额 |
| Core／Waves 与 Result | 出兵表、清波、奖励、胜负 | 平台广告、账号或付费逻辑 |
| Cocos Presentation | 场景、角色、骨骼动作、镜头、UI、音效和轻量特效 | 再算一次伤害或结算 |
| PlatformAdapter | 指针／触控命令、存储、前后台、安全区、后续 SDK 能力 | 分叉三套玩法数值与规则 |

玩法核心是纯 TypeScript 数据和状态更新，可在无渲染条件下测试。平台输入先转成统一命令，核心接收命令并输出事件，Cocos 只展示结果。资源共用源文件，不假定各端最终二进制完全相同。第一切片只写确有用途的接口，不提前搭建通用插件框架。

平台能力采用“有则使用、无则隐藏”，首切片不依赖 Steam 成就、云存档、TapTap 登录或抖音广告。Steam 官方说明发布产品不强制集成 Steamworks API，因此 SDK 不作为当前玩法前置。[Steamworks API 说明](https://partner.steamgames.com/doc/sdk/api)

### 3.3 输入、屏幕与最小存档

- 统一操作：点击／轻触战位 → 显示可造单位、价格、射程或阻挡说明 → 点制造；选中本身不扣款。空白处／返回取消选择，不取消已经施工的任务。
- 桌面不依赖鼠标悬停才能看到关键信息；移动端不依赖右键、拖拽或小面积角色点选。UI 命中先消费输入，避免穿透点击战场。
- 点制造后立刻显示工程猫“前往／施工”、进度和忙碌原因；仅前往阶段显示取消及全额退款说明。重复触摸和鼠标事件须去重。
- 以横屏 16:9 为基准，另检查 16:10、4:3 和 20:9；保持路线、四战位、水晶完整，扩展背景或留边，不裁掉核心区域。刘海、安全区与平台覆盖控件不得遮住制造、开波、暂停按钮。
- 触控主按钮热区以不小于 48×48 逻辑单位为初始目标，文字和热区在目标真机检查；该尺寸是本项目设计目标，不是平台已验证标准。
- 第一次进入准备阶段用短提示引导“选战位、造猫、开波”，提示可关闭；水晶受伤、盾猫倒地、资金不足和工程猫忙碌均有可见反馈，不能只靠音效。
- 首切片只存音量、画质／提示设置和已完成三波的本地记录，保存带 schemaVersion 的小数据；不做跨设备同步和对局中途恢复。损坏／不兼容版本存档回退默认值，不阻塞开局。手动退出／重开有清晰的“结束本局”提示；教程完成状态归入提示设置。
- 切后台只冻结当前内存中的一局，返回显式继续；若进程被杀，重新加载后从新局开始并清楚告知。不能承诺恢复到离开时的战斗。波前检查点只在后续八波扩展时再评估，本三波版本不引入。

### 3.4 现在落实的小游戏资源约束

2026-10-07 核对的抖音官方“代码包”规则：普通未分包小游戏总包上限 20MB；配置分包时，默认整体包不超过 20MB、主包不超过 4MB、单个分包不超过 20MB。官方另列开通虚拟支付后的体积调整，本项目不依赖该条件，也不套用 Unity／团结转换路径的特殊规则。[抖音官方代码包规则](https://developer.open-douyin.com/docs/resource/zh-CN/mini-game/develop/guide/basic-function/subpackages/introduction)

本项目先按分包方案留空间：主包内部目标 ≤ 3.5MB，主包与分包总和目标 ≤ 18MB，实际以构建产物和届时工具校验为准。把加载 UI、必要代码放主包，一张桥地图及一猫一狗的共用资产作为首局资源，不带入扩展兵种和高分辨率概念图。需要完整首局资源后才开放“开始”。

若实测超预算，依次裁剪未用引擎模块、去重复纹理／音频、降低贴图与特效、整理分包；仍不满足再评估远程资源及其失败重试、缓存、域名和托管要求，相关账号与费用另行确认。仅分包不会减少总资源体积。

Cocos 有抖音专用构建和分包流程，但具体补丁、开发者工具版本、AppID 与宿主兼容必须在实际接入时复核；不能用本机浏览器结果替代小游戏验收。[Cocos 抖音构建说明](https://docs.cocos.com/creator/3.8/manual/zh/editor/publish/publish-bytedance-mini-game.html)

## 4. 状态、统一时钟与结算

状态流：加载 → 准备 → 战斗 → 波结算 → 下一轮准备／胜利。水晶生命归零时立即失败，失败优先于清波和胜利。

- 每次准备由玩家手动开波，没有自动倒计时。工程猫忙碌或核心资产未齐时禁用开波按钮并显示原因。
- 只有“尚未出生数 = 0 且场上活狗 = 0”才能清波，清波奖励只发一次。
- 清波先让所有盾猫满血、倒地者复活，再开放下一轮准备操作；水晶不恢复。
- 第 3 波清波且水晶仍存活则胜利。失败／胜利后不再出生、攻击、移动、施工或发奖，只有结算 UI 和重开等非战斗操作继续工作。

### 所有战斗时间只走一套时钟

用固定步长模拟时钟，首测建议 1/60 秒；出兵、移动、攻击前摇、冷却、飞箭、施工与表现动作均消费同一模拟时间。不为每个兵种另设独立战斗定时器。

暂停或切后台立即冻结模拟与音频；返回时清空累积时间，等待玩家显式继续，不追补后台期间的战斗。重开从初始状态恢复资金、水晶、波次、角色、战位、出生编号与事件队列，清理旧飞箭、监听、计时器、对象和音频。

每个固定步内按稳定顺序处理：移动／产生攻击与命中事件 → 伤害与死亡 → 漏怪与水晶伤害 → 失败判定 → 清波／胜利判定。施工完成事件必须在终局判定后复核状态，失败或胜利同一步不允许出现幽灵完工。相同输入、配置和出生顺序应可重复得到相同规则结果。每局带独立 sessionId；旧局异步加载回调、完工回调和事件到达时先核对会话与状态，失效就丢弃。

加载失败页提供重试和返回。核心模型、地图或必要 UI 缺失时不开局，也不用白模顶替正式猫狗交付；可选音效失败可静音继续并提示。重试只重试当前会话，不让已返回或重开的旧请求重新挂入场景。

## 5. 施工与资金边界

制造允许在准备和战斗阶段下令，暂停、波结算和终局不接受新任务；首切片无升级或拆除。一次只有一个施工任务，无排队。

1. 接受前校验阶段、资金、战位类型、占用和工程猫是否空闲。只有合法接受才扣款、锁位，并生成唯一 taskId。
2. 工程猫走独立预设通道；不受伤、不挡路、不攻击，不使用动态寻路。
3. 前往途中可以取消：只退款一次、只解锁一次，工程猫原地空闲。开始施工后不可取消。
4. 空位在完工前不参战；有效完工后才生成战斗单位，并释放任务锁。忙时仍可查看其他战位、价格和射程，但不能下第二个任务，不扣款、不排队；常驻显示工程猫当前目的地、前往／施工状态和进度。
5. 已倒地盾猫仍占战位，不能当空位再造。终局取消未完成任务并停止模拟，不允许再生成完工结果；终局不再开放购买，重开直接恢复初始经济。
6. 战斗中施工遇到清波：先结算该波；未终局则保留任务并在准备阶段继续，工程猫完成或前往中取消后才可开下一波。第三波胜利则按终局清理任务。

后续 8 波若开放升级／拆除：仅准备阶段允许；升级仍走施工流程，每单位最多一次，属性在完工时更新。拆除返还总投入的 75%，向下取整；战斗中禁拆。

## 6. 阻挡、选敌和实际命中

### 阻挡和放行

每道防线独立管理阻挡名额。狗沿路线进度移动，进入防线时：有名额就分配展示槽并停住；满额就写入该防线的放行标记。已放行或被倒地盾猫释放的狗不能被同一道防线重新抓回，后方防线仍可阻挡。

盾猫倒地立即释放全部目标，本波停止工作但仍占战位；清波后满血复活。每道盾前设 2 个固定接敌槽，代理互不重叠并处于双方有效攻击距离内；分配时即占名额，狗沿短引导段进入槽位，进入可攻击位置后才开始攻击计时。放行狗沿预设侧绕曲线走过防线，不能从盾或已阻挡狗身体穿过；工程猫使用另一条连续便道。

规则中的权威位置、模型脚底位置与飞箭碰撞位置必须对应。路线参考进度 s 保持单调用于防线越线和选敌，绕行按实际路径弧长维持移速，不能为保持旧到达时间而让狗侧滑加速。路线长 24 指中心参考路线，侧绕可能增加实际行程，须记录实测到达时间。禁止刚体互挤与动态寻路；若密集 8 狗仍明显重叠，先调道路宽度、接敌槽和绕行曲线，重新验证射程和难度。

盾猫只攻击自己阻挡的狗，狗只攻击阻挡自己的盾猫，不攻击远程猫。盾猫在自己阻挡的目标中按 spawnId 从小到大选敌；弩猫按“距离水晶最近，再按 spawnId”选敌。换目标不返还已经开始的冷却，不积攒空闲期间的连击。

### 弩箭必须飞到才扣血

- 起手和发射前都验证目标存活且处于射程内；发射前失效就取消这一箭，不返还已开始的攻击间隔。
- 每箭有唯一 projectileId、锁定 targetId 和已命中标记。按当前目标位置追踪，不换靶、不用刚体；发射后允许追到射程外。
- 以本步前后位置作线段扫掠，触达目标碰撞代理半径时才产生统一伤害事件，避免高速穿透。代理半径须是明确配置并与模型尺寸核对。
- 目标先死或箭存活超过 2 秒时消散，不凭动画完成回调补伤害。
- 同箭至多提交一次命中和一次伤害；死亡、击败奖励也按唯一实体 ID 去重。
- 清波、失败、胜利和重开清空飞箭与待命中事件；暂停冻结前摇、冷却和飞行。

近战同样由 Battle 按模拟时间判定伤害，动作不另算一次。狗首次攻击也必须等满 1 秒，不能在阻挡瞬间凭空多打一击。

### 经济仅证明“买得起”

v0.4 把初始小鱼干从 160 调到 **165**，价格与击败／清波奖励不变。这是对首波少量漏怪即买不起第二弩的规划修正，仍需实际对局验证。

假设前波全部击败、无漏怪，各波开始前累计可分配收入为：

- 第 1 波前：165。
- 第 2 波前：165 + 8 × 3 + 30 = 219。
- 第 3 波前：219 + 10 × 3 + 30 = 279。

采购候选：第 1 波前盾 + 弩花 135，余额 30；第 2 波前再造弩花 75，余额 9；第 3 波前再造盾花 60，余额 9。总投入 270 ≤ 279。

漏怪容错按累计计算：设第一波漏 a 只、第二波漏 b 只，其他狗均被击败且水晶存活。

- 第 2 波前可用余额 = 84 − 3a；a ≤ 3 时可以买第二弩。
- 买过第二弩后，第 3 波前可用余额 = 69 − 3(a + b)；a + b ≤ 3 时可以买最后一盾。
- 例如第一波漏 3 只、第二波不漏，第 3 波前恰好 60；第一波漏 3 只、第二波再漏 1 只，则只有 57，无法按候选顺序买齐。

容错指前两波累计最多 3 只，不是每波都可漏 3 只；漏怪仍扣水晶生命并损失收入。首版不加入隐性救济或保底奖励，失败时说明原因并可重开。

这些只是条件预算。射程覆盖、建造时间、阻挡和伤害时序均未实测，不能据此宣称能通关。T5 必须以完整对局和逐波结果证明可行性；数值调试先改现有配置，不靠增加系统掩盖问题。

历史记录保留：v0.3 以初始 160 计算全歼累计收入 160／214／274，候选采购后余额分别 25／4／4，首波漏 2 只时第二波前只有 73，低于弩价 75。v0.4 的 +5 调整用于缓和该脆弱边界，并非已证明平衡。

原 8 波方案仍按旧初始 160 保留算术：击败奖励合计 524，全局累计收入 924，第 8 波前累计收入 750，2 盾 + 3 弩 + 3 投弹全部升满成本 1085。若未来只把初始改为 165、其余旧 8 波假设完全不变，则两项累计收入分别变成 929／755；仍不表示能通关。扩展前须重做特殊狗规则、波表和可行采购路径。

## 8. 目标视觉、资产与性能

### 8.1 最终游戏画面的目标

画面采用干净、温暖的风格化低至中面数实时 3D，固定斜俯视，本轮角色比例提案约 3.5–4 头身，拟人双足，最终以用户审阅样图后确定。此前 v0.3 的 4.5–5 头身作为历史探索保留，不同时作为当前硬性验收。小溪、石桥与猫方水晶形成主景，前后两道防线一眼可辨；地面盾猫承接道路，弩猫使用木台，工程猫便道连续通过桥区，不凭空跨越水面。

角色轮廓优先于表面细节：工程猫有工具和施工姿态，盾猫的大盾与稳重站姿、弩猫的弩和平台可直接识别；狗的口鼻、耳形、体态和装备与猫明显区分。简化手、毛发和衣服，不做耳尾物理、布料模拟、电影级景深或大面积炫光。

战斗画面必须同时看清路线、四个战位、前后阻挡、水晶和工程猫目的地。特效只用于解释行为：施工进度、盾击接触、实际飞箭、轻微命中反馈、漏怪／水晶受伤；命中特效不能早于规则命中。使用图标、文字或形状补足颜色信息，不只靠红绿区分状态。

目标概念图应覆盖全局战场、交战与阻挡、工程施工、触屏操作布局，使用同一张地图和同一角色方向。概念图用于审美与布局讨论，尚待用户审阅；不能据图认定模型、UI、动画、性能或美术已验收。当前文档不引用未入库文件，不建立假图片路径。

### 8.2 从样本到游戏资产

先验收一只猫基础体和一只狗基础体，再用装备区分猫的工作。保留 Blender 源文件，先用共用骨架与装备挂点导出 glTF／GLB 样本并验证 Cocos 实际导入；不假设导出成功就意味着材质、坐标轴、骨骼和动画全部兼容。[Cocos glTF 说明](https://docs.cocos.com/creator/3.8/manual/zh/asset/model/glTF.html)

角色、装备、场景分开制作。优先验证工程施工、持盾攻击、弩射，以及狗的走路／攻击／受击／退场；最容易穿帮的弩射持物和狗走攻衔接先过样本验收，再批量生产。检查脚底、肩肘、持物、尺度、权重、材质槽、动作命名和镜头辨识度。两个同类实例必须可同时播放不同动作，资源可以共享、实时姿态不能串联。若 glTF 某项导入不符合预期，先在样本上简化／烘焙材质与动作；确需换交换格式时保留源资产，在小样中验证再批量生产。

最小来源记录随资产保存：文件或 ID、来源／生成工具、日期、输入参考来源、适用条件链接及待确认项。不另建大套审批文件。条件尚未确认的素材先标记，不作为可公开发布素材；不假定后续付费自动覆盖旧资产。

### 8.3 先定预算，再用真机修正

| 项目 | 首测设计预算／目标 | 验证方式 |
| --- | --- | --- |
| 角色 | 每角色约 3000–6000 三角面；共享身体材质与 1024 级贴图，移动低档可用 512 | 检查导入后实际网格、材质、纹理内存及视觉可辨识度 |
| 首切片压力 | 最多 12 狗 + 4 战斗猫 + 1 工程猫，共 17 个骨骼单位；四战位全建、飞箭与施工同时存在 | 合成最坏压力场景与完整三波分别测，不能只测一只猫 |
| 渲染 | 单主光、简化地面影，限制透明叠加和粒子；初始目标 draw call ≤ 100 | 各端实际构建采样；超额先查材质、阴影、骨骼与特效 |
| 帧表现 | 移动低档与抖音先以 30 FPS 为底线目标；Windows 可再争取 60 FPS | 完成加载后在目标设备连续 10 分钟压力／重复对局，目标平均 ≥ 30 FPS、P95 ≤ 40ms，单列 > 100ms 长帧次数；首载独立记录，无持续热降频或明显操作卡顿 |
| 加载与恢复 | 可见加载进度、失败重试；资源齐备才开局 | 冷／热启动、断网、失败重试、切后台30秒、被杀进程后重进分别记录 |
| 重开与内存 | 连续重开 10 次，无旧事件、对象或资源持续增长 | 记录重开前后对象与内存变化，排除正常缓存后检查是否持续上涨 |

这些是项目内部起始预算，全部未实测，不能写成已达到或平台保证。目标设备尚未确定：技术验证阶段先记录可用的 Windows PC、Android 真机和抖音宿主设备，再据实际低档设备定最低支持范围；模拟器只做布局和流程补充。记录设备、系统、宿主／浏览器、分辨率、画质、构建、包体、首载时间、帧时和内存。

性能不足时先关动态阴影、后处理和多余特效，再降渲染分辨率、贴图、模型／骨骼更新成本；不先改玩法数量。需要减少同屏敌人时，必须重审波表与难度，不能静默改变规则。后续 8 波才额外验证 30 狗 + 8 战斗猫 + 1 工程猫，共 39 单位的扩展压力。

## 9. 开发前准备与执行顺序

当前先完成四件事：范围与规则无明显冲突；目标视觉可供审阅；三平台接口与资源约束写清；每项重要风险有可执行方案、测试标准与退路。计划审阅完成不等于实测完成；不要以“问题全解决”掩盖仍需原型验证的部分。开发、安装和平台操作在后续获准后开始。

实际开发顺序：T1 Cocos 底座与最小跨平台技术验证 → T2 真实猫狗资产样本 → T3 施工与经济 → T4 战斗与三波 → T5 完整对局与布阵 → T6 本地完整试玩。T2 可与 T3／T4 白模规则验证并行，最终在同一真实猫狗构建中合验。

T1 先把三种构建的输入、生命周期、最小存储和资源路径验证计划落实，不等大批美术完成才检查导出。可用且获准的环境先做小样；Windows／Android／抖音所需工具、设备或 AppID 未具备时记录为未验证，不假称本机预览覆盖三端，也不为此先做商店上传。正式三端验收与上传分开，见第 10 节。

T6 完成至少意味着：一张桥地图、可辨识猫狗、全部 3 波、胜负、重开、暂停／后台恢复、加载失败提示均可实测；提供启动说明与完整录像，关键边界测试有实际结果。运行命令由实现后的真实工程确定，不在空仓库预写不存在的启动命令。

核心测试覆盖：重复下单与取消不重复扣款／退款；盾满额放行和倒地释放；过线敌人不回抓；箭实际命中和目标先死；组间空场不提前清波；漏怪与击败不双发奖；水晶归零与清波同一步只失败；终局无幽灵施工；暂停与后台无追补；连续重开无旧事件污染；不同输入与屏幕不改变规则。

T5 除稳定通关外，还需双弩、前盾前弩、前盾后弩对照、漏怪预算和工程猫等待评估。当前弩射程 5、横距路线 3，直线理论覆盖 8 个路线单位；狗速 1 时覆盖约 8 秒，弩理论输出 30 伤害／秒，存在纯弩支配风险。这是待验证分析，实际还受起手、飞箭、选敌和侧绕影响。至少一个可重复遭遇应体现盾猫降低漏怪，第二道防线要实际接敌；不强行要求纯弩必输。若盾或后线无价值，先调射程、移速、密度与战位，重测全三波。工程等待过长先缩短便道路程，不增加瞬移或另设准备阶段移速。三波主要验证闭环与兵种价值，不宣称已经具备正式商业版本的内容量或长期可玩性。具体勾选项见[执行清单](EXECUTION_CHECKLIST.md)。用必要日志、完整录像和简短逐波表说明结果，不生成大量证据包、守卫脚本或 hash 锁。

## 10. 三平台验收、发布与后续扩展

1. 本地完整切片后，对同一版本分别完成 Windows 原生、Android 原生、抖音小游戏的构建、操作、生命周期、资源加载与性能验收。未具备环境的端明确列为未测试。
2. Windows 需真实 Windows 构建和运行；Android 需安装包及真机；抖音需专用构建、开发者工具、实际宿主测试。比较同一规则输入的结算结果，不以画质完全相同作要求。
3. 游戏达到计划完成标准后，再分别准备 Steam、TapTap 和抖音账号、上传材料、签名、必要 SDK、审核和渠道要求。开发工具预览／技术测试不算平台发布；实际上传、账号授权、购买或法律协议步骤单独确认。
4. 素材来源和适用使用条件在公开发布前核实。商业化、广告收入、付费功能与经营／资质层面调查后置，不承诺收入、留存、审过或未经验证的上线日期。
5. 根据三波通关、兵种价值、等待时间与性能结果决定是否扩为八波；补齐特殊狗、投弹猫、升级／拆除和新波表后重做预算与回归测试。

三平台可以分批达到可交付状态，不能让其中一端未验证的事实被“跨平台完成”掩盖。若抖音资源或性能经降级仍不可接受，先暂停该端量产，保留 Windows／Android 路线并重新讨论该端画质或范围；不自动改回 Three.js、不换引擎重写，也不擅自取消用户要求的平台。
